PROJECT PURPOSE
A full-stack email scheduling system where users can log in, upload recipients, schedule emails, and monitor scheduled and sent emails.

COMPLETE EMAIL SCHEDULING FLOW

User
→ Google Login
→ Dashboard
→ Compose New Email
→ Upload CSV/TXT recipients
→ Set subject, body, start time, delay and hourly limit
→ Frontend calls backend API
→ Backend validates request
→ Email jobs stored in PostgreSQL
→ Idempotency key generated
→ Jobs added to BullMQ/Redis as delayed jobs
→ Scheduled email indexed in Elasticsearch
→ BullMQ waits until scheduled time
→ Worker picks up job
→ Redis-backed hourly rate limit checked
→ If limit available:
    → Email sent through configured EmailProvider (Resend API / Mock)
    → Database updated to SENT
    → Elasticsearch index updated
    → Prometheus metrics updated
    → Slack notification sent for SENT event
→ If rate limit exceeded:
    → Job is delayed/rescheduled to next available window
    → Slack notification sent for RATE_LIMITED event

DATABASE RESPONSIBILITIES

PostgreSQL is the source of truth.

Store:
- Users (Google OAuth profile)
- Senders
- Email jobs
- Status
- Scheduled time
- Sent time
- Idempotency keys

REDIS RESPONSIBILITIES

Redis is used for:
- BullMQ job storage
- Delayed job scheduling
- Distributed rate-limit counters
- Coordination that works across multiple workers/instances

BULLMQ WORKFLOW

- API creates delayed jobs
- Redis persists jobs
- Worker processes jobs
- Configurable concurrency
- Minimum delay between sends
- Jobs survive backend restarts
- Idempotency prevents duplicate sends

RATE LIMITING FLOW

Worker receives job
→ Check Redis counter using sender + current hour
→ Limit available?
    YES → Increment counter → Send email via EmailProvider
    NO → Do not drop job
          → Calculate next available time
          → Reschedule/delay job
          → Notify Slack

Limits are configurable through environment variables.

ELASTICSEARCH FLOW

PostgreSQL is the source of truth
→ Important email fields are indexed in Elasticsearch
→ Dashboard search API queries Elasticsearch
→ Users can search scheduled and sent emails by recipient, subject, or other indexed fields.

SERVER RESTART FLOW

Server stops
→ PostgreSQL data remains persisted
→ Redis/BullMQ jobs remain persisted
→ Docker volumes preserve infrastructure data
→ Server/worker starts again
→ BullMQ continues processing delayed jobs
→ Previously sent jobs are not resent because of database status and idempotency checks.

SLACK NOTIFICATION FLOW

Webhook configured via SLACK_WEBHOOK_URL
→ Email lifecycle triggers (SCHEDULED, SENT, FAILED, CANCELLED, RATE_LIMITED)
→ Backend sends asynchronous HTTP webhook notification
→ If Slack is not configured or fails, scheduler continues without breaking.

HIGH LOAD BEHAVIOR

System handles 1000+ emails scheduled around the same time:
- Jobs are persisted in Redis
- BullMQ queues the jobs
- Configurable worker concurrency controls parallel processing
- Minimum delay throttles sending
- Hourly rate limits prevent exceeding provider limits
- Excess jobs are rescheduled instead of dropped
- Database and idempotency checks prevent duplicate sends
